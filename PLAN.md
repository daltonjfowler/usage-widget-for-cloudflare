# Build and handoff

## Scope

Free Android home-screen widget for account-wide Cloudflare usage charges and Workers compute. User authorized the full local build and creation of this standalone Desktop folder. Device: Pixel 7 running GrapheneOS. User is comfortable installing an APK.

## Implemented

- Direct HTTPS billing API, no server or Cloudflare deployment.
- Account setup and connection verification, encrypted token, disconnect, account ID entered by the user (empty by default with a hint).
- Current billing-cycle cost totals and every returned service, separate currencies.
- Workers Standard raw request/CPU recognition, conditional paid-plan allowance bars in the app and widget.
- Compact resizable widget (SizeF variants STRIP/WIDE/MEDIUM/LARGE/TALL/XL, default 4x1) and a Workers request/CPU counter with pace projection, USD overage estimate, and unidentified-row diagnostics. The "+N" family token was removed in favor of currency-separated family overflow lines. The XL variant (key 180x330) is what a full-height three-row home-screen cell receives; it shows the full breakdown plus an allowance-left line, pace line, and next-bill line.
- Workers identification fixes from the first on-device screenshot: the exclusion token check runs on ServiceName and ChargeDescription only, so rows Cloudflare groups under the "Workers & Pages" family are recognized while Pages Functions is still excluded; request and CPU units now also accept the "million ..." variants (multiplier 1,000,000); a "Copy row names" button and Billing.rowLabels expose every returned row for developer diagnosis; when no Workers rows are identified the MEDIUM footer, LARGE metrics view, and TALL/XL extra line all say so instead of hiding the meters silently.
- Upcoming charges: best-effort /subscriptions fetch, listed subscription fees with renewal dates, a current-cycle usage projection, and an estimated next-bill figure. The DEFAULT_ACCOUNT constant was removed; the account field starts empty with a hint.
- Home-screen widget, demo, details, manual and three-hour background refresh.
- Cached data and clear offline/stale/permission-denied states.
- Build script and billing/Android regression tests.
- In-app updates (versionCode 3): sideload-safe self-updates for a phone with no Play Store. A Cloudflare Worker with static assets hosts `latest.json` and the signed APK at `usagewidget-updates.daltonjfowler.workers.dev` (written by `scripts/publish.ps1`, deployed by Dalton). `Updater` checks `latest.json` over HTTPS, and on a tap downloads the APK, verifies its SHA-256 and its signer certificate against the running app, then installs through the platform `PackageInstaller`; on any mismatch it deletes the file and installs nothing. An Updates card in the app shows the running build, a Check for update button, an available line with size and notes, an Update button with download progress and honest failure text (including the GrapheneOS Network note), and an editable source URL stored in preferences. A daily persisted `RefreshJob.UPDATE_CHECK` job (24 h, `NETWORK_TYPE_ANY`, flex 4 h) posts one notification per new version code on a low-importance Updates channel; nothing downloads or installs on its own. The check is a plain GET with no query string and no device id, and the Worker keeps no logs.
- Restyle (version 1.1): gradient card with a softer stroke, the family breakdown as a two-column ledger (names left, amounts right-aligned, zero amounts dimmed), meter bars that turn hot at 80% of the allowance, a tighter total, and extra group spacing on XL only. LARGE and TALL drop the group margins in code because their live two-line footer sits within a few dp of the 180x200 and 180x256 keys. Known limit, pre-existing: at the narrow 180dp TALL key the "Left:" line wraps and the next-bill line ellipsizes; a real three-row Pixel cell is 276dp wide and shows all three. The docs and releases PNGs were re-exported from the Robolectric renders; docs/device-pixel7.png predates the restyle.

- Week view and monthly reset (version 1.2, unreleased): the app's headline now shows **this cycle's** usage charges, not a sum across every billing cycle Cloudflare returns. Previously `MainActivity` and the widget rendered `Billing.total()`, which merges cost across all returned cycles, so a two- or three-cycle response read as a single ever-growing figure that never reset monthly (seen on device as a ~$0.68 "lifetime" total). The headline is now `Billing.usageThisCycle()` (latest cycle only) in the app and all widget variants; when the response spans more than one cycle the app adds a quiet "Running total since <date>" line so the cumulative figure is still available. New `Billing.currentCycleStart()`, `multipleCycles()`, `runningTotal()`, `earliestCycle()`; `period()` now anchors to the current cycle start. A new "THIS WEEK · Daily usage" card draws a seven-day bar chart with a Charges / Requests / CPU toggle. History is local-only: the billable-usage endpoint gives no per-day series, so `History` records one sample per Cloudflare coverage date on each successful refresh and connect (cumulative current-cycle charges per currency, Workers requests, CPU ms), capped at 40 days. Each bar is the day-over-day increase; a cumulative drop at a cycle boundary is read as the new cycle's usage so far, never a negative bar. Days with no snapshot render as hollow outlines and the first-ever sample as a faint baseline, keeping "no data" distinct from "zero usage". Charges pick USD when present, else the largest currency in the latest sample. `BarChartView` draws the bars by hand in the card palette. Nothing leaves the device; no new permissions or endpoints.

- Widget customization (version 1.2, unreleased): a "Widget appearance" card in the app sets two global display preferences applied to every placed widget via `UsageWidget.updateAll`. A background-transparency slider (`SeekBar`, 10..100% opacity; never fully invisible) and five accent swatches (Amber default, Sky, Mint, Violet, Coral). Stored in `Store` as `widget_opacity` and `widget_accent` (clamped on read). `UsageWidget.applyAppearance` runs after each variant is built: below full opacity it replaces the card background with a solid ARGB fill (`BG_BASE` at the chosen alpha; the launcher rounds widget corners on Android 12+), and it recolors the title and refresh glyph to the accent. The accent also drives the Workers meter bars (`meterRow` takes the warm color; the over-allowance bar stays a fixed red warning). Preferences are global, not per-widget; a future per-widget config Activity would thread `appWidgetId` through the builders. On-device only; no new permissions.

- UI declutter (version 1.3, shipped 2026-09-17): the app is split into two tabs, Usage and Settings, shown once connected or in demo (first-run stays a simple single page). Usage holds the charges overview, the weekly chart, upcoming charges, and the breakdown; Settings holds the account card, widget appearance, updates, and about. Tabs toggle card visibility in place (no re-render), so form text and scroll survive. THE BREAKDOWN is now collapsed by default: a one-line summary ("N services with charges · K included at no charge"), a Show/Hide toggle, compact rows (service name trimmed of its "(First … included)" tail, quantity · cost on one muted line), and the no-charge rows tucked behind a secondary toggle. "Copy full row names" still exposes every raw label for diagnostics. Update-notification taps open the Settings tab; a successful connect lands on Usage.

## Validation

- Signed release APK compiles with debugging disabled. Personal signing key stays under ignored `private/`; preserve it for future updates.
- Final run (version 1.1): 101 tests passed (BillingTest 49, SubscriptionsTest 14, AndroidBehaviorTest 28, WidgetPreviewTest 10). Native Android rendering exported a real widget preview and a 192x192 launcher-icon preview, visually inspected.
- Version 1.2 built, gated, signed, and shipped on 2026-09-17 using the project-local toolchain in `.tools/` (JDK 17 + Android SDK 35): `assembleRelease` + `testDebugUnitTest` + `lintRelease` all green — 6 test files, 133 tests, 0 failures (`HistoryTest` 14 included), lint clean. The release APK is versionCode 4 / 1.2, signed with `private/release.jks`; its signer cert SHA-256 (`1050743d…ff2e`) matches the published 1.1 APK, so the in-app updater accepts it. Published to the update Worker and confirmed live: `https://usagewidget-updates.daltonjfowler.workers.dev/latest.json` serves version_code 4. The earlier standalone JDK-25 math check (26/26) is superseded by the real suite.
- `applyAppearance` uses `setBackgroundColor` with an alpha channel (certain to render) rather than a background tint, so a translucent widget shows square corners except where the launcher rounds them (it does on Android 12+). If a rounded translucent card is wanted instead, switch to a rounded solid drawable plus `setBackgroundTintList`. The Robolectric widget preview PNGs (`build/previews/*.png`) and the `docs/`/`releases/` screenshots were not re-exported for 1.2; regenerate them when convenient. The app screenshot showing the new "This week" chart needs a device/emulator capture (Robolectric renders the widget only).
- Release pipeline (2026-09-17): `scripts/ship.ps1 -Notes "…"` runs the whole flow in one command — build + full gate + sign, then `verify-apk.ps1` (APK versionCode must equal build.gradle; signer must equal the pinned published cert), a no-downgrade check against live latest.json, `latest.json` write, `wrangler deploy`, and a live-endpoint confirmation. Bump versionCode AND versionName first or publish refuses. All native tools run via `cmd /c … > log 2>&1` because Windows PowerShell 5.1 turns a native stderr line into a terminating error under `-ErrorAction Stop` (a javac deprecation note otherwise looked like a failed build; pwsh 7 does not do this). wrangler auth and the signing key stay on the machine; no secrets pass through a session.
- Android lint: 0 errors, warnings only. Remaining warnings concern English-only strings and deliberate synchronous preference commits on the background executor.
- Release signature verified with Android apksigner (APK signature v2, RSA 3072). Package `app.usagewidget`, version 1.1 (2), min SDK 31, target SDK 35, no debuggable flag. APK: 91204 bytes. SHA-256: 73ba6c6d0457a61437f0dbd7782b398b477698e16c06ccd08abf72763ac837ad (recorded in `releases/SHA256SUMS.txt`).
- No physical Android device attached to ADB at build time.
- In-app updates are on-device only past the unit tests: `UpdaterTest` proves the check states, the checksum and signer verifications (which delete the file and never install), the one notification per version code, and the daily job's `NETWORK_TYPE_ANY` and 24 h period with a fake network Source and a swapped certificate reader (no socket, no Keystore, no real signed APK). The real file download, the signer check on a genuine APK, the `PackageInstaller` dialog, the unknown-sources redirect, and the notification are Dalton's to verify on the phone (device API is above what Robolectric can emulate). `scripts/publish.ps1` was proven with `-NoDeploy` only; the Worker is never deployed by the worker session. See `docs/checklist-updates.md`.
- Workers request/CPU identification was verified against the live row names from the device on 2026-09-12. The user should still compare the widget's request count against the Workers overview counter (Requests / CPU time) in the Cloudflare dashboard.
- The first on-device screenshot (Pixel 7, GrapheneOS, tall widget) showed no identified Workers rows at all: the request and CPU meters and the pace line were absent while the dashboard reported six product families and 171.63k Workers requests. The app's diagnostics list then showed the actual cause: Cloudflare sends an empty ConsumedUnit for these rows (the app shows "units (unspecified)") and names them "Workers Standard Requests (first 10M are included)" and "Workers CPU ms (first 30M are included)", with a ChargeDescription that repeats the name plus "usage measured in Count". Identification now falls back to the service name when the unit is empty or "Count", KV and build-minute rows stay excluded, the exclusion check runs on ServiceName and ChargeDescription only, the "million ..." unit variants were added, and unidentified snapshots surface a "not identified" line plus a "Copy row names" button. Regression tests mirror the exact live row shapes. A fresh on-device check of the meters is still pending.
- Existing Wrangler OAuth login successfully identifies the account, but a read-only GET to the billing endpoint returns HTTP 403 (code 10000). The user must create a Billing Read API token and enter it in the app. No deployment token was copied into this project.
- On-device check passed on 2026-09-12 (Pixel 7, GrapheneOS, three-row widget): 166.95K requests (2%), 87.84K CPU ms (<1%), six families listed, "Left: 9.83M requests · 29.91M CPU ms", pace line, and "Next bill about $5.45 · Sep 14". The dashboard counter read 171.63k at a later data time than the billing snapshot (latest data 2026-09-11 UTC), which explains the gap. Missing metric amounts intentionally remain unavailable rather than zero.
- The /subscriptions endpoint and response shape are unverified against a live account; field names come from the docs only, and parsing is lenient with a reject-and-preserve policy.
- Subscriptions failures never fail the usage refresh; a failed subscriptions fetch keeps the last saved list and records a separate error.
- The estimated next bill excludes tax, credits, zone plans, and proration; zone plans need zone permissions and are not covered.
- Sub-monthly renewals are counted once for a single period.
